# AlumnixHub: архітектура, технології, алгоритми та тестування

Документ підготовлено 7 жовтня 2026 року за фактичним кодом проєкту. Це опис
реалізованої системи, а не твердження про виконання всіх можливих вимог до
виробничого застосунку. Результати тестування наведено за останніми перевірками.

## 1. Призначення та зв'язок із темою роботи

AlumnixHub — вебсистема для комунікації університетської спільноти та
адміністрування Telegram-бота. Вона об'єднує профілі студентів і випускників,
каталог менторів, новини, події, особисті повідомлення, опитування, сповіщення
та адміністративні інструменти.

Зв'язок із темою «Вебсистема адміністрування ботів для комунікації випускників
університету» забезпечує не лише наявність Telegram-посилання. Через сайт
адміністратор керує матеріалами, користувачами, аудиторіями розсилок,
модерацією отриманих через бот новин, файлами, тематичними довідниками,
підключенням Telegram та результатами доставки. Сайт є центральним місцем
керування, а бот — додатковим каналом доступу до спільних даних.

Важлива межа: реалізовано інтеграцію одного налаштованого Telegram-бота.
Система не є універсальним конструктором довільної кількості незалежних ботів.
У дипломі не варто приписувати їй мультиботність, якщо відповідної вимоги та
реалізації немає.

## 2. Тип архітектури

Проєкт має архітектуру модульного моноліту. Вебмаршрути, бізнес-правила,
Telegram-інтеграція та інтелектуальні алгоритми належать одному застосунку,
але розділені на модулі. Вони використовують спільну базу даних.

Це не мікросервіси: бот не є окремим незалежним сервером із власною базою.
Це також не React SPA: основні сторінки формуються сервером із HTML-шаблонів.

```text
Браузер користувача                       Telegram-клієнт
         |                                      |
         | HTTP                                 | Telegram API
         v                                      v
    FastAPI / Uvicorn <---- фонові цикли обробки бота
         |
         +-- routers: маршрути, форми, API, перевірка доступу
         +-- services: реєстрації, повідомлення, модерація, переклад
         +-- ml: ранжування, TF-IDF, скорочення текстів
         +-- Jinja2 templates + CSS + JavaScript
         |
         v
      SQLAlchemy
         |
         v
      SQLite на сервері + завантаження + приватні резервні копії

Зовнішні інтеграції: SMTP, Telegram Bot API, DeepL, офіційні джерела КПІ.
```

Переваги такого рішення: один процес розгортання, спільні правила для сайту
та бота, відсутність дублювання бази, зрозуміле налагодження. Обмеження:
відмова застосунку впливає і на сайт, і на бота; фонові задачі не винесені
в окремий сервер черг; масштабування потребує додаткового проєктування.

## 4. Організація коду

Основні каталоги та відповідальність:

- `app/main.py`: створення FastAPI, підключення маршрутів, middleware, шаблонів, запуск і завершення фонових задач.
- `app/config.py`: налаштування бази, пошти, Telegram, URL застосунку й секретів.
- `app/db.py`: SQLAlchemy engine, `SessionLocal`, базовий клас ORM і залежність `get_db()`.
- `app/models.py`: опис сутностей і зв'язків бази.
- `app/security.py`: паролі, підписані сесії, токени підтвердження та відновлення.
- `app/deps.py`: визначення поточної особи, повторна перевірка акаунта та адміністративних прав.
- `app/routers/`: контролери окремих функціональних модулів.
- `app/services/`: спільні бізнес-правила, інтеграції, довідники та фонові процеси.
- `app/ml/`: статистичні й NLP-алгоритми.
- `app/templates/`: HTML-сторінки Jinja2.
- `app/static/`: стилі, JavaScript, зображення та завантаження.
- `app/data/`: публічні структуровані довідники країн, спеціальностей і викладачів.
- `scripts/`: імпорт, підготовка даних, розгортання й допоміжні перевірки.
- `tests/`: автоматичні сценарії перевірки.
- `docs/`: документація й результати перевірок.

Не слід описувати систему як повністю ізольовану «чисту архітектуру»:
деякі маршрути безпосередньо працюють з ORM і містять бізнес-перевірки.
Сервісний шар застосований там, де правила мають використовуватися повторно.

## 5. Життєвий цикл HTTP-запиту

Приклад: користувач відкриває особистий профіль.

1. Браузер надсилає запит до `/profile` разом із cookie сесії.
2. Uvicorn передає його застосунку FastAPI.
3. Залежність читає й перевіряє підпис сесії.
4. Для захищеної дії сервер перевіряє наявність, активність і блокування користувача в базі.
5. `get_db()` відкриває SQLAlchemy-сесію.
6. Маршрут отримує користувача, довідники й додаткові поля профілю.
7. Jinja2 формує HTML із даних.
8. Браузер відображає сторінку; JavaScript додає мовну й інтерактивну поведінку.
9. Сесія бази закривається після обробки запиту.

Після надсилання форми використовується POST. Сервер повторно перевіряє дані:
браузерні обмеження не вважаються достатнім захистом. Коректна операція зазвичай
завершується перенаправленням HTTP 303; некоректна — повідомленням про помилку.

| Сутності | Призначення |

| `PageView`, `PageDuration`, `UserActivity` | Перегляди, тривалість взаємодії та активність |

| `TelegramBroadcast`, `TelegramRecipientDelivery` | Розсилки та стан доставки окремим отримувачам |
| `ContentTranslation` | Кеш перекладів за хешем початкового тексту |
| `BackupRecord`, `AdminAudit` | Резервні копії та журнал адміністративних дій |

Зв'язок користувачів і подій є «багато до багатьох» через `Registration`.
Унікальність пари `user_id + event_id` не дозволяє двічі зареєструвати ту саму
особу на одну подію. Унікальний email та індекси допомагають забезпечити
цілісність і прискорити типові запити.

SQLite — файл на сервері, а не база в браузері. Записи зберігаються після
перезапуску контейнера завдяки окремому підключеному каталогу. База може
зростати зі збільшенням кількості даних; фіксованого ліміту «на 10 чи 100
користувачів» у системі немає. Практичні обмеження визначаються диском,
запитами й одночасними записами. Максимальну місткість навантажувальні
перевірки цього проєкту не встановили.

Схема створюється через `Base.metadata.create_all()`, а зміни існуючих таблиць
виконують власні функції `services/migrate.py`. Це не повноцінна система
версійованих міграцій Alembic. Перед оновленням потрібна резервна копія.

## 7. Акаунти, ролі та професійний статус

Треба розрізняти чотири незалежні поняття:

1. Роль у спільноті: студент, випускник, учасник спільноти.
2. Адміністративні права: дозвіл на керування системою, зокрема делегований через `AdministratorGrant`.
3. Професійний статус: наприклад, «Викладач університету» або «Шукаю роботу».
4. Поточна посада: професор, доцент, Backend Engineer тощо.

Прапорець менторства також окремий: він не повинен автоматично надавати
адміністративні права. Активність, блокування й підтвердження email — це
стани акаунта, а не професійний статус.

Для автоматичного переходу студента у випускники використовується
`services/alumni_role.py`. Якщо коректний рік випуску менший за поточний,
роль стає `alumni`. Перевірка працює при вході, збереженні профілю,
захищених запитах і запуску сервера. У 2026 році випуск 2025 означає
випускника, а випуск 2026 ще не запускає перехід. Порожні, майбутні й
суперечливі дати не використовуються для автоматичного підвищення.

Поточна структура містить теперішню посаду й компанію, але не повну
хронологічну історію всіх місць роботи. Це межа моделі, а не прихована функція.

## 8. Автентифікація та захист

Пароль перед збереженням обробляється `hash_password()` через PBKDF2-SHA256.
Зберігається хеш із сіллю, а не початковий пароль. Однакові паролі можуть
давати різні хеші. Під час входу `verify_password()` перевіряє відповідність;
дешифрування пароля не відбувається.

Після входу браузер отримує підписану cookie сесії. Це не JWT і не шифрування
всіх даних сесії. Підпис дозволяє виявити зміну вмісту без знання серверного
секрету. Для захищених дій роль і стан акаунта додатково перевіряються в базі,
щоб відкликання прав або блокування не залежало лише від старої cookie.

Первинні адміністратори підтримуються приватним `admins.csv` із хешами
паролів; додаткових адміністраторів можна призначати через сайт. Керування
адміністраторами потребує окремого права, підтвердження дії й пароля.

Реєстрація передбачає email-підтвердження. Відновлення доступу використовує
випадковий токен; його SHA-256 зберігається в базі з терміном дії. SHA-256
токена і PBKDF2 пароля виконують різні завдання та не є взаємозамінними.

Для повідомлень і критичних адміністративних операцій використані часові
токени підтвердження/CSRF. Наприклад, токен розмови пов'язаний з конкретною
парою відправника та отримувача. Наявність цих механізмів не доводить
однаковий CSRF-захист кожного маршруту системи.

Важливі обмеження: поточне з'єднання з сайтом HTTP, не HTTPS; підпис cookie
не захищає транспорт від перехоплення. У відновленні пароля існує діагностичний
режим показу посилання при вимкненій/несправній пошті; для відкритого випуску
таку поведінку потрібно окремо переглянути. Повний аудит безпеки не виконаний.

## 9. Валідація профілю й довідники

Основні правила дат:

- дата народження не може бути в майбутньому;
- рік випуску — ціле число від 1965 до поточного року;
- випуск не раніше вступу;
- якщо дата народження задана, випуск не раніше ніж через 15 років після року народження;
- вступ не раніше року народження, у межах прийнятого сервером діапазону;
- порожня необов'язкова дата відрізняється від некоректної введеної дати.

JavaScript змінює допустимі межі полів, але сервер повторює перевірку.
Старі помилкові дані не стають правильними лише від додавання валідації:
у перевіреній базі залишилися чотири записи з некоректними датами.

Країни зберігаються у структурованому JSON-довіднику: назви українською й
англійською, коди та транслітерація. Код країни відокремлений від міста,
що зменшує кількість довільних несумісних назв.

Спеціальності поділено на історичні коди до 2015 року, тризначні коди
2015–2024 і літерно-цифрові коди від 2025 року. Рік допомагає обрати
класифікацію, але не повинен самовільно переписувати код із диплома.
Адміністратор може додати чи деактивувати запис довідника через сайт.
Зіставлення старих і нових напрямів не завжди є взаємно однозначним.

## 10. Події та реєстрація

Подія має назву, повний і короткий опис, адресу, час початку й завершення,
дедлайн реєстрації, місткість і зображення. Адміністратор керує ними на сайті.
Початок обов'язковий; завершення має бути пізніше початку; дедлайн не може
бути пізніше початку; кількість місць має бути додатною. Час із явно заданим
поясом нормалізується до UTC; довільний час без поясу сам собою не означає
виконану повну локалізацію часових зон користувачів.

Сервіс `event_registration.register()` спільний для сайту та Telegram.
Він перевіряє активність і підтвердження email, існування події, повторну
реєстрацію, дату/дедлайн та доступні місця. Перед перевіркою місткості
виконується оновлення того самого запису події без зміни значення, щоб
серіалізувати конкурентні операції в транзакції. Додатково діє унікальний
індекс реєстрацій. Це захист конкретної операції, не доказ максимальної
надійності під будь-яким навантаженням.

QR-код містить URL сторінки події з переходом до зони реєстрації. Він не
містить пароль, не обходить авторизацію й не реєструє людину автоматично.
Генерація QR — детерміноване кодування посилання, а не штучний інтелект.

Особисті повідомлення зберігаються у власній таблиці. Розмова доступна
придатним активним користувачам із підтвердженим email; не можна почати
розмову із собою, а отримувач має мати публічний профіль. Доступ до конкретної
розмови та токен відправлення перевіряються сервером. Поточне сервісне правило
не вимагає однакового потоку: окремі старі пояснювальні тексти про таке
обмеження не слід використовувати як точний опис фактичного коду.

Опитування мають окремі питання та відповіді, керуються адміністратором,
дозволяють збирати й агрегувати інформацію спільноти. Треба розрізняти
реальні відповіді та синтетичні дані для тестів. Тестові відповіді не є
результатами дослідження реальних випускників.

## 12. Telegram: справжній механізм роботи

У `main.py` під час запуску, якщо Telegram увімкнено, створюються фонові
задачі отримання оновлень, доставки й відповідей. Вони скасовуються при
завершенні застосунку. Запити до Telegram виконуються через Bot API.

Реалізовано polling, не webhook. Приблизно кожні п'ять секунд виконується
`getUpdates`; його `offset` зберігається в `TelegramState`. Запити до
зовнішнього API винесені у потік через `asyncio.to_thread`, щоб не виконувати
блокувальний мережевий виклик безпосередньо в циклі asyncio.

Послідовність: оновлення Telegram → перевірка приватного чату → зв'язок
із профілем → розбір команди/кнопки → робота зі спільною базою → запис
відповіді → окрема задача відправлення. Ідентифікатор оновлення використовується
для уникнення повторної обробки. Є обмеження частоти окремих дій.

Тому для роботи бота потрібен запущений сервер застосунку. Натискання
«Start» у Telegram саме по собі не запускає процес на університетському сервері.
Одночасний polling того самого бота різними процесами може викликати конфлікт.

Прив'язування профілю використовує персональне одноразове посилання.
Секретний код має обмежений строк дії, у базі зберігається його хеш.
Підключення Telegram не надає автоматично браузерної сесії адміністратора.
Команда `/stop` відкликає підписки та підключення відповідно до реалізованих правил.

Бот дозволяє читати новини й події, переглядати свої реєстрації, зареєструватися
на подію, перейти до профілю/повідомлень/опитувань, надсилати підтримувані файли.
Новина через `/submit_news` створюється як неопублікована чернетка та потрапляє
на модерацію. Адміністратор публікує її на сайті. Читання потім використовує
той самий запис `News`; не існує окремих несинхронізованих копій для бота й сайту.

Важлива межа: кнопка реєстрації акаунта в боті відкриває `/register` на сайті.
Повністю автономний Telegram-майстер реєстрації з перенесенням аватара
Telegram наразі не є підтвердженою реалізованою функцією. Створення та
редагування подій адміністратора також відкривається на сайті, а не повністю
виконується всередині діалогу Telegram.

## 13. Керування розсилками

Адміністратор формує текст і аудиторію на сайті. Для користувачів враховуються
підключення, актуальна придатність акаунта та згода на відповідні категорії
сповіщень. Результат для кожного отримувача зберігається окремо: це дозволяє
розрізняти заплановані, успішні та невдалі доставки.

Для зовнішніх повідомлень не можна обіцяти «exactly once»: після мережевого
збою результат виклику іноді невідомий. Код обережно ставиться до повторів,
щоб не створювати дублікати розсилок. Стан `connected` означає робоче
з'єднання бота, а не підтвердження доставки кожної розсилки.

## 14. ШІ та NLP: точні терміни

Система використовує локальні статистичні й правилові алгоритми. Наявність
папки `ml` не означає навченої нейромережі або ChatGPT. Алгоритми не треба
описувати як самонавчальні, якщо вони не перенавчаються на накопичених даних.
У поточних рекомендаціях ваги задаються програмно.

### 14.1. Тематичні персональні рекомендації

`services/personalization.py` обслуговує `/api/personal-suggestions`.
Алгоритм працює з каталогом предметних тем, а не із частотою довільних слів.
`InterestTopic` містить ключ, назви двома мовами, активність і синоніми.
Розпізнавання враховує назви, ключі, синоніми та задані шаблони.

Джерела інтересів: явний вибір користувача, зареєстровані події,
час на сторінках подій і новин за останні 30 днів. Якщо є явні інтереси,
вони мають пріоритет над непрямими припущеннями. Якщо інтересів немає,
алгоритм не вигадує їх із слів «та» чи «що», а може повернути порожній список.

Кандидати: до 300 майбутніх подій та до 100 опублікованих новин. Події,
на які користувач уже зареєстрований, заповнені або із закритою реєстрацією,
відкидаються. Раніше переглянуті конкретні матеріали також виключаються.
Матеріал без спільної тематичної категорії не отримує рекомендацію.

Формула оцінки в поточному коді:

```text
score = 5 × сума ваг спільних тем / сума ваг інтересів
      + 0.25 × частка часу в розділі цього типу
      + 0.15, якщо тип матеріалу збігається з поточним розділом
```

Явна тема має вагу 1.0. Непрямі сигнали мають менші ваги, до 0.5.
Користувачу повертаються три найкращі матеріали та тематичні причини вибору.
Наприклад, інтерес «Кібербезпека» може дати рекомендацію події про захист
мереж, але не довільної статті з великою кількістю сполучників.

Обмеження: це керований словник, а не необмежене семантичне розуміння.
Невідомі синоніми й теми потрібно додавати в каталог. Час перегляду —
наближений поведінковий сигнал, не доказ зацікавлення конкретної людини.

### 14.2. Окремий гібридний механізм подій

У `routers/web.py` також викликається `ml/hybrid.py`. Це інший шлях,
його не можна видавати за тотожний тематичним спливаючим рекомендаціям.
Він використовує тексти подій із історії реєстрацій, TF-IDF та косинусну
подібність, а також популярність і часовий фактор.

```text
hybrid_score = 0.60 × NLP_similarity
             + 0.25 × popularity
             + 0.15 × freshness
```

TF-IDF враховує слова та двослівні послідовності. Профіль користувача є
зваженою сукупністю текстів історії. Ваги зростають за порядком записів;
це не рівнозначно повній моделі часової деградації за точними датами.
Англійські стоп-слова вилучаються, але цей механізм має окремі обмеження
для українських службових слів. Для єдиної послідовної політики рекомендацій
доцільне майбутнє узгодження обох шляхів. Не слід заявляти, що весь проєкт
уже використовує лише тематичний алгоритм.

### 14.3. Формування коротких описів

`ml/summarizer.py` реалізує екстрактивне скорочення:

1. Нормалізація пробілів і поділ тексту на речення.
2. Перетворення речень та повного документа у TF-IDF-вектори.
3. Обчислення косинусної подібності речення до документа.
4. Вибір кількох речень із найвищою оцінкою.
5. Обмеження довжини й, за потреби, додавання назви.

```text
cosine(a, b) = (a · b) / (||a|| × ||b||)
```

Це вибір частин наявного тексту, а не генерація нових фактів великою мовною
моделлю. Стандартний виклик використовує до двох речень і приблизно 180
символів; preview може задавати іншу межу. Обрізання й додавання трикрапки
мають свої нюанси, тому це не гарантія завершеного речення для будь-якого тексту.
Переваги: локальна робота й відсутність обов'язкової оплати зовнішньому
провайдеру генерації. Недоліки: обмежена якість перефразування, простий
поділ на речення та англійський список стоп-слів.

### 14.4. Асистент

Асистент має правилову маршрутизацію запитів і парсер часових виразів.
Він може запропонувати розділ системи або відфільтрувати події за періодом.
Слова `upcoming`, `this week`, англійські назви місяців обробляються через
шаблони. Це не повний двомовний семантичний пошук: українські часові
формулювання й тематична фільтрація довільних запитів підтримуються обмежено.

У перевіреному маршруті не викликається API GPT, немає RAG-пошуку по всій
базі й вільної генерації відповідей. QR-коди, звичайні SQL-фільтри та
автоматичний перехід ролі є програмними алгоритмами, а не ШІ.

## 15. Двомовність і переклади

Інтерфейс має три рівні локалізації:

1. Статичні підписи: українсько-англійські словники JavaScript.
2. Явні пари: атрибути на кшталт `data-ops-uk` і `data-ops-en`, окремі імена.
3. Динамічні тексти: `content_text()` позначає поле; клієнт спочатку шукає
   локальний переклад, а за потреби звертається до серверного API й DeepL.

Переклади DeepL кешуються за SHA-256 початкового тексту та версією механізму.
Зміна початкового тексту змінює ключ кешу. За недоступності перекладу
залишається оригінал і може з'явитися пояснювальне повідомлення.
Це зовнішня інтеграція: частина динамічного контенту передається провайдеру,
що треба враховувати в політиці обробки персональних даних.

Імена транслітеруються або мають окремий англійський варіант; їх не потрібно
перекладати як звичайну фразу. Дати форматуються відповідно до мови.
Не слід обіцяти безпомилковий переклад будь-якої довільної адреси чи тексту:
це залежить від словника, кешу й доступності провайдера.

## 16. Профілі викладачів

Для 15 викладачів зібрано публічні факти з офіційних сторінок: імена,
посади, академічні напрями, фото та професійні контакти. Спеціальність
диплома відокремлено від дисципліни, яку людина викладає. Невідомі факти
не заповнюються довільними кодами або припущеннями.

Створені акаунти є технічними тестовими акаунтами власниці проєкту,
а не підтвердженими особистими акаунтами викладачів. Адреси входу зарезервовані
для тестового використання, не є реальними скриньками. Справжні контакти
збережені окремо. Паролі випадкові, у базі хешовані; початкові паролі
містяться тільки в приватному файлі, виключеному з Git і Docker-контексту.

Є позначка непідтвердженої участі у менторстві, немає адмін-прав,
сповіщення вимкнені. Повні імена залишені в метаданих джерела, у картках
використано ім'я та прізвище. Для 14 є офіційні фото; для одного —
аватар з ініціалами. Публікація каталогу не означає отримання згоди всіх осіб.

## 17. Аналітика, журнал та резервні копії

Middleware фіксує перегляди й активність; клієнтський облік тривалості
дає додатковий сигнал для рекомендацій. Адміністратор може аналізувати
відвідуваність, популярні сторінки та взаємодію. Необхідно відрізняти
реальні показники від активності тестів, ботів і перевірок: навіть GET-запити
навантажувального тесту можуть потрапляти в статистику.

Адміністративний журнал фіксує автора, тип дії, шлях і результат.
Тіла запитів і паролі навмисно не включаються в цей журнал.

Резервний архів може містити SQLite-знімок, необхідні налаштування,
адміністративні дані й файли завантажень. Через це архів є приватним:
права доступу обмежуються, він не повинен потрапляти в GitHub.
Перевірка копії включає контрольну суму та відновлення в окрему тимчасову
базу з `PRAGMA integrity_check`. Робоча база не перезаписується тестовим
відновленням. Для планових копій передбачено збереження останніх 14;
їх створення залежить від увімкнення фонового механізму.

## 18. Розгортання

На сервері сайт працює у Docker на основі Python 3.11. Усередині
контейнера Uvicorn слухає 8000, зовні опубліковано 4063.
База й завантаження підключені окремими каталогами сервера, а секрети
передаються через приватну конфігурацію, не через публічний код.

```text
http://77.47.192.6:4063 → порт 8000 контейнера → Uvicorn → FastAPI
```

Telegram polling запускається разом із застосунком. Docker має політику
перезапуску `unless-stopped`, що не тотожно кластерній відмовостійкості.
Оновлення включає резервну копію, підготовку джерел, збирання образу,
коротку зупинку старої версії, запуск нової та перевірку. Попередній
контейнер залишено зупиненим для можливого відкату. Відкат коду після
міграцій не завжди дорівнює безпечному відкату схеми; копія потрібна окремо.

Код опубліковано у двох GitHub-репозиторіях. GitHub зберігає код, а не
саму робочу базу, `.env`, облікові паролі чи резервні архіви.

## 19. Як реалізацію логічно поділити на етапи

Це реконструкція структури робіт за підсумковим кодом, не вигаданий
погодинний журнал розробки:

1. Модель предметної області: користувачі, матеріали, участь, повідомлення, права.
2. Серверний каркас FastAPI, ORM, шаблони й конфігурація.
3. Реєстрація, email-підтвердження, сесії та відновлення доступу.
4. Профілі, каталоги, освітні довідники та валідація.
5. Адміністративні форми для матеріалів, опитувань і прав.
6. Сервіс спільної реєстрації на події й приватне листування.
7. Інтелектуальні алгоритми, аналітика та персоналізація.
8. Telegram polling, прив'язування, команди, модерація та доставки.
9. Локалізація, адаптивні стилі, резервне відновлення.
10. Ізольовані тести, серверні перевірки й Docker-розгортання.

## 20. Основні складні тест-кейси

Кожен сценарій нижче описує перевірювану вимогу. Не всі кроки виконувалися
в реальному браузері під час останнього аудиту: частина підтверджена
автоматичними тестами або HTTP-перевірками. Навмисні розсилки проводяться
тільки в тестовому середовищі та за згодою адресатів.

### TC-01. Вхід, блокування та відкликання доступу
Передумова: активний підтверджений користувач. Увійти правильним паролем,
перевірити неправильний пароль, заблокувати акаунт у тестовій базі й
повторити захищений запит зі старою сесією. Очікування: правильний вхід
успішний; помилковий пароль не допускає; старої cookie недостатньо
для обходу актуального блокування. Паролі не зберігаються відкритим текстом.

### TC-02. Межі дат і незмінність даних після помилки
Передумова: профіль із коректними даними. Надіслати народження 2002,
вступ 1940; майбутнє народження; випуск 1905; випуск до вступу;
випуск раніше 15 років після народження. Очікування: HTTP 400,
жоден некоректний набір не перезаписує профіль. Потім перевірити коректний
набір і необов'язкові порожні поля. Відсутня дата не прирівнюється до помилки.

### TC-03. Автоматична роль випускника
Передумова: студент із роком випуску меншим за поточний. Перевірити
збереження, вхід і запуск системи. Очікування: роль `alumni`;
повторна перевірка не створює нових змін; професійний статус збережений.
Випуск цього року, майбутній випуск, порожній або суперечливий рік
не змінюють роль. Адміністратор і учасник спільноти не підвищуються цим правилом.

### TC-04. Межі часу подій і місткості
Створити подію із завершенням до початку, однаковими початком і завершенням,
дедлайном після початку, порожнім початком і місткістю 0. Очікування:
відхилення до збереження. Коректна подія з часовим поясом порівнюється
після нормалізації. Те саме перевірити при редагуванні наявної події.

### TC-05. Останнє місце та повторна реєстрація
Передумова: майбутня подія з одним доступним місцем і двома придатними
користувачами. Спробувати конкуруючі реєстрації та повторити успішну.
Очікування: місткість не перевищена, повторної пари користувач-подія немає.
Окремо перевірити закритий дедлайн і минулу подію. Справжній конкурентний
стрес-тест не слід підміняти двома послідовними HTTP-запитами.

### TC-06. Делегування адміністративних прав
Передумова: адміністратор із правом керування адміністраторами та
підтверджений користувач. Призначити права з правильним паролем, CSRF і
підтвердженням; повторити з підробленим токеном, неправильним паролем
та без права делегування. Очікування: лише дозволена дія успішна, є запис
аудиту. Після відкликання стара сесія не повинна зберігати адмін-доступ.

### TC-07. Приватне листування й ідентифікація учасників
Передумова: дві активні підтверджені особи та третя стороння.
Надіслати повідомлення з коректним токеном, підмінити отримувача,
спробувати чужу розмову та повідомлення самому собі. Очікування:
сторонній доступ і токен іншої пари відхиляються; дозволене повідомлення
зберігається лише в потрібній розмові. Заблокований користувач не допускається.

### TC-08. Приватність після перезапуску
Приховати профіль у тестовій базі, перевірити пошук і двічі запустити
ініціалізацію. Очікування: прихований профіль не стає публічним;
перезапуск не скасовує вибір користувача.

### TC-09. Telegram: одноразовість і припинення підписки
Створити код прив'язування, використати його в приватному чаті,
повторити та перевірити прострочений код. Потім надіслати `/stop`.
Очікування: одноразовий код не використовується повторно, прострочений
не приймається, відкликана підписка не потрапляє в дозволену аудиторію.

### TC-10. Telegram-новина та вебмодерація
Підключений користувач надсилає `/submit_news` із заголовком і текстом.
Адміністратор перевіряє чернетку на сайті й публікує її. Очікування:
до модерації новина не видима як опублікована; після дозволеної публікації
доступна з того самого джерела даних; повтор одного update не дублює новину.
Порожній текст і перевищення лімітів відхиляються.

### TC-11. Пояснювані рекомендації та негативні приклади
Задати інтерес «Кібербезпека», створити релевантну й нерелевантну події.
Додати тексти лише зі словами «та», «що». Очікування для тематичного API:
спільні предметні теми дають результат і причину; службові слова — ні.
Заповнені, закриті й уже зареєстровані події не рекомендуються.
Явні інтереси переважають непрямі поведінкові припущення.

### TC-12. Скорочення тексту та відсутність нових фактів
Подати довгий текст, короткий текст, порожній опис і службові слова.
Очікування: немає помилки векторизації; результат базується на вхідному
тексті; довжина обмежується відповідно до реалізації. Оцінювати читабельність
також вручну: наявність результату не доводить його змістової якості.

### TC-13. Українська та англійська версії
Відкрити головну, профіль і події; переключити мову в обидва боки.
Очікування: «Вітаємо»/«Hello», переклади посад і локацій, правильні місяці,
незмінні коди спеціальностей та коректні варіанти імен. Відключити провайдер
динамічного перекладу: інтерфейс не має ламатися, оригінал залишається доступним.

### TC-14. Резервна копія та пошкоджений архів
Створити копію тестової бази, перевірити контрольну суму, відновити в
тимчасове місце та виконати integrity_check. Змінити копію й повторити.
Очікування: коректна копія проходить, пошкоджена відхиляється; робоча база
не перезаписується. Архів недоступний як публічний статичний файл.

### TC-15. Ідемпотентний імпорт технічних менторів
Запустити імпорт двічі, змінити професійний статус одного імпортованого
профілю та повторити. Очікування: немає дублікатів або зміни паролів;
ручний непорожній статус збережений; справжні контактні email не стають
логінами; не з'являються адмін-права чи небажані розсилки.

### TC-16. QR-код і доступ
Придатний користувач отримує PNG-код існуючої події; анонімний повторює
запит. Очікування: для авторизованого коректний PNG; для анонімного доступ
заборонений. Відкриття URL із коду не обходить звичайну реєстрацію на подію.

## 21. Фактичні результати й межі тестування

Останній повний набір: 264 успішні автоматичні тести й два попередження
тестового клієнта HTTPX. Пройшли також JavaScript-перевірки форми та
перекладів. На сервері перевірялися публічні й захищені маршрути, вхід
технічного користувача, заборона адмін-дій, некоректні дати, QR, стан
Telegram, цілісність бази та відновлення резервної копії.

Серверна перевірка показала нуль порушень зовнішніх ключів і хешовані
паролі наявних користувачів. Це не оцінка складності їхніх паролів і не
доказ відсутності всіх вразливостей. Візуальна перевірка останніх змін
не завершена через недоступність браузерного інструмента.

JMeter-план існує для шести публічних сторінок: 5 відвідувачів, 5 раундів,
150 запитів. У документації є попередні результати: один запуск мав одну
помилку, повторний — без помилок. Це історичний легкий baseline, а не
новий тест останньої версії та не визначення максимального навантаження.
HTTP-тест також не виконує JavaScript і не замінює Lighthouse чи браузер.

## 22. Основні питання на захисті

**Чому це відповідає темі?** Вебсистема керує контентом, підписками,
аудиторіями, модерацією та доставками Telegram-каналу спільноти, а не лише
посилається на чужого бота.

**Чому моноліт?** Для цього масштабу він спрощує спільні правила,
транзакції та розгортання. Мікросервіси додали б операційну складність без
підтвердженої потреби; розділення можна виконати при зростанні навантаження.

**Де знаходяться дані?** У серверному SQLite-файлі в підключеному каталозі.
Вони не живуть у пам'яті браузера й не зникають із перезапуском контейнера.

**Чи може будь-хто керувати ботом?** Ні. Права перевіряються сервером;
прив'язування Telegram не замінює адміністративний вхід у браузері.

**Чим рекомендації відрізняються від пошуку?** Пошук виконує явний запит,
а персональний алгоритм ранжує доступні матеріали на основі інтересів і
поведінкових сигналів. Його результат містить тематичні пояснення.

**Чи використано нейромережу?** Для локальних рекомендацій і скорочення
описів — ні: використані правила, TF-IDF та статистичні оцінки. DeepL —
окремий зовнішній сервіс перекладу, не власноруч навчена модель.

**Чи бот працює без сайту?** Його фонові задачі працюють у процесі застосунку;
без цього запущеного процесу команди не обробляються.

**Чи отримали викладачі особисті акаунти?** Ні, створено технічні тестові
акаунти; участь у менторстві не підтверджена. Публічні контакти відокремлені
від технічних логінів.

**Чи доводять тести повну готовність?** Ні. Вони підтверджують конкретні
сценарії. HTTPS, аудит залежностей, велике навантаження й повні ручні
сценарії Telegram/пошти потребують окремого підтвердження.

## 23. Що не варто стверджувати в дипломі

- Не називати поточну базу PostgreSQL або хмарною СУБД лише через драйвер у залежностях.
- Не називати всі інтелектуальні функції генеративним ШІ чи ChatGPT.
- Не приписувати асистенту необмежене розуміння українських запитів.
- Не стверджувати, що обидва шляхи рекомендацій уже об'єднані в один тематичний.
- Не заявляти автономну Telegram-реєстрацію з імпортом фото як завершену функцію.
- Не видавати технічні профілі та синтетичні опитування за реальну участь людей.
- Не називати 264 успішні тести доказом відсутності всіх багів.
- Не стверджувати HTTPS, високодоступний кластер, безперервне масштабування чи аудит безпеки, яких немає.

## 24. Короткий підсумок для усної відповіді

«Мій проєкт — модульна вебсистема на FastAPI зі спільною базою даних для
сайту та Telegram-бота. Адміністратор керує матеріалами, користувачами,
підписками й розсилками через сайт. Бот отримує команди через polling і
використовує ті самі бізнес-правила, зокрема реєстрацію на події. Інтелектуальні
функції включають тематичні рекомендації, гібридне ранжування та екстрактивне
скорочення текстів. Паролі хешуються, доступ перевіряється сервером,
передбачені аудит і резервне відновлення. Реалізацію перевірено автоматичними
й серверними тестами; обмеження щодо HTTPS, ручних перевірок і деяких
Telegram-функцій я відокремлюю від підтверджених можливостей».
